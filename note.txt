# How to Store Project Knowledge for AI Assistants
# =================================================
# This is a universal guide. Follow this structure for ANY project
# so that any AI assistant can immediately understand and work on it.


# ================================================================
# 1. WHERE TO PUT IT
# ================================================================

# Create a folder at the project root:
#
#   your_project/
#   └── instructionAI/        ← all AI knowledge goes here
#       ├── SKILL.md           ← entry point (AI reads this FIRST)
#       ├── architecture.md    ← project structure
#       ├── ...                ← topic-specific files
#       └── references/        ← (optional) large docs, schemas, examples
#
# WHY a dedicated folder?
# - AI tools scan for SKILL.md or AGENTS.md files automatically
# - Keeps instructions separate from source code
# - Easy to copy between projects or share with teammates


# ================================================================
# 2. FILE STRUCTURE (what to create)
# ================================================================

# REQUIRED FILES (create these for every project):
#
# ┌─────────────────────┬──────────────────────────────────────────────┐
# │ File                │ Purpose                                      │
# ├─────────────────────┼──────────────────────────────────────────────┤
# │ SKILL.md            │ Entry point. Project overview + file index.  │
# │                     │ AI reads this first to know what exists.     │
# │                     │ Must have YAML frontmatter (name, desc).     │
# ├─────────────────────┼──────────────────────────────────────────────┤
# │ architecture.md     │ File/folder map, what each file does,        │
# │                     │ dependency graph, key design decisions.      │
# ├─────────────────────┼──────────────────────────────────────────────┤
# │ conventions.md      │ Code style, naming rules, patterns used,     │
# │                     │ known gotchas, what is safe/dangerous to     │
# │                     │ change.                                      │
# └─────────────────────┴──────────────────────────────────────────────┘
#
# OPTIONAL FILES (add based on project type):
#
# ┌─────────────────────┬──────────────────────────────────────────────┐
# │ File                │ When to add                                  │
# ├─────────────────────┼──────────────────────────────────────────────┤
# │ data_pipeline.md    │ Project processes data (ETL, ML, analytics)  │
# │ api_spec.md         │ Project has APIs (REST, GraphQL, gRPC)       │
# │ environment.md      │ Project has simulation/env (RL, games)       │
# │ deployment.md       │ Complex deploy process (Docker, K8s, CI/CD)  │
# │ safety_and_risk.md  │ Project has safety-critical rules            │
# │ model_spec.md       │ Project uses ML models                       │
# │ database.md         │ Project has database schema/migrations       │
# │ testing.md          │ Complex test setup or test conventions       │
# │ auth_and_security.md│ Auth flows, secrets management, permissions  │
# └─────────────────────┴──────────────────────────────────────────────┘


# ================================================================
# 3. SKILL.md FORMAT (the entry point)
# ================================================================

# Every SKILL.md must follow this format:
#
# ---
# name: your-project-name
# description: >
#   One paragraph describing what this project does.
#   This is what AI uses to decide if this skill is relevant.
# ---
#
# # Project Name — AI Instruction Set
#
# ## What this project is
# [2-3 sentences explaining the project]
#
# ## Instruction files in this folder
# [Table listing every file in instructionAI/ and its purpose]
#
# ## Critical rules for any AI working on this project
# [Numbered list of absolute rules that must never be broken]
#
# RULES FOR WRITING SKILL.md:
# - Keep under 500 lines
# - The YAML frontmatter (name + description) is what triggers
#   AI to load this skill — make the description specific
# - Critical rules should be things that cause BREAKAGE if violated
# - Don't put details here — link to the specific file instead


# ================================================================
# 4. WHAT TO INCLUDE vs EXCLUDE
# ================================================================

# ✅ INCLUDE (stable knowledge that rarely changes):
#
# - Project architecture and file responsibilities
# - Code conventions and naming patterns
# - Data flow / pipeline diagrams
# - API contracts and interface specs
# - Safety rules and constraints
# - Known gotchas and common mistakes
# - How components connect (dependency graph)
# - What is safe vs dangerous to modify
# - Design decisions and WHY they were made
# - Environment setup steps
#
# ❌ EXCLUDE (things that change frequently):
#
# - Performance metrics and benchmark results
# - TODO lists and pending actions
# - Account numbers, API keys, passwords
# - Deployment timelines and schedules
# - Specific version numbers (put in requirements.txt instead)
# - Bug reports and issue trackers
# - Meeting notes or decision logs with dates
#
# RULE OF THUMB: If it will be outdated in 2 weeks, don't put it
# in instructionAI/. Put it in a separate living document instead.


# ================================================================
# 5. HOW TO WRITE EACH FILE
# ================================================================

# Follow these principles for every .md file:
#
# A) STRUCTURE
#    - Start with a 1-2 line summary of what this file covers
#    - Use ## headers to break into sections
#    - Use tables for specs, parameters, and comparisons
#    - Use code blocks for exact formats, commands, formulas
#    - Use bullet lists for rules and constraints
#
# B) VOICE
#    - Write as facts, not instructions ("The bot uses X" not "You should use X")
#    - Be specific — exact values, exact file paths, exact function names
#    - Explain WHY, not just WHAT (design rationale prevents AI from
#      "improving" things that are intentional)
#
# C) LENGTH
#    - Each file: 50-200 lines ideal, max 300 lines
#    - If a file exceeds 300 lines, split it into subtopics
#    - Keep the total instructionAI/ folder under 50KB
#
# D) CROSS-REFERENCES
#    - Reference other files by name: "See architecture.md for..."
#    - Don't duplicate content across files
#    - SKILL.md is the only file that lists all other files


# ================================================================
# 6. ALTERNATIVE STORAGE LOCATIONS
# ================================================================

# Different AI tools look for instructions in different places.
# For maximum compatibility, you can ALSO place rules in these
# standard locations:
#
# ┌────────────────────────────┬───────────────────────────────────┐
# │ Location                   │ Which AI reads it                 │
# ├────────────────────────────┼───────────────────────────────────┤
# │ .agents/skills/*/SKILL.md  │ Gemini / Antigravity (auto-load)  │
# │ .agents/AGENTS.md          │ Gemini / Antigravity (rules)      │
# │ .claude/                   │ Claude Code                       │
# │ .cursor/rules/             │ Cursor                            │
# │ .github/copilot-instructions│ GitHub Copilot                   │
# │ CONVENTIONS.md (root)      │ Most AI tools check root .md      │
# │ .ai/                       │ Generic convention (growing)      │
# └────────────────────────────┴───────────────────────────────────┘
#
# RECOMMENDED APPROACH:
# 1. Keep the master copy in instructionAI/ (your main folder)
# 2. Optionally symlink or copy SKILL.md to .agents/skills/ for
#    tools that auto-discover skills
# 3. Put a one-liner in root AGENTS.md pointing to instructionAI/:
#    "For all project knowledge, see instructionAI/SKILL.md"


# ================================================================
# 7. TEMPLATE FOR A NEW PROJECT
# ================================================================

# Step-by-step to set up instructionAI/ for any new project:
#
# 1. Create the folder:
#      mkdir instructionAI
#
# 2. Create SKILL.md with:
#      - YAML frontmatter (name + description)
#      - "What this project is" section
#      - Empty "Instruction files" table (fill as you add files)
#      - "Critical rules" list (even if just 2-3 rules)
#
# 3. Create architecture.md with:
#      - File tree (copy from `tree` or `ls -R` output)
#      - One sentence per file explaining its role
#      - Dependency graph (what imports what)
#
# 4. Create conventions.md with:
#      - Naming conventions used in the codebase
#      - File organization pattern
#      - Known gotchas (things that surprised you while building)
#      - "Safe to change" vs "Dangerous to change" lists
#
# 5. Add topic-specific files as needed (see section 2)
#
# 6. Update SKILL.md's file table whenever you add a new file
#
# 7. Review every ~month: remove anything that became outdated


# ================================================================
# 8. EXAMPLE: MINIMAL instructionAI/ FOR A WEB APP
# ================================================================

# instructionAI/
# ├── SKILL.md              (project overview, 3 critical rules)
# ├── architecture.md       (file tree, component responsibilities)
# ├── conventions.md        (React patterns, state management, CSS approach)
# ├── api_spec.md           (endpoint list, auth flow, error format)
# └── database.md           (schema, migrations, query patterns)
#
# Total: 5 files, ~15KB — enough for any AI to work on the project
# without asking 20 questions first.


# ================================================================
# 9. EXAMPLE: MINIMAL instructionAI/ FOR AN ML PROJECT
# ================================================================

# instructionAI/
# ├── SKILL.md              (project overview, critical rules)
# ├── architecture.md       (file tree, pipeline stages)
# ├── conventions.md        (code style, gotchas)
# ├── data_pipeline.md      (data sources, preprocessing, splits)
# ├── model_spec.md         (architecture, hyperparams, I/O format)
# └── observation_pipeline.md (features, scaling, vector format)
#
# Total: 6 files, ~20KB


# ================================================================
# 10. GOLDEN RULES
# ================================================================

# 1. SKILL.md is ALWAYS the entry point — AI reads it first
# 2. Each file covers ONE topic — don't mix architecture with conventions
# 3. Include WHY, not just WHAT — prevents AI from "fixing" intentional design
# 4. Never include secrets, keys, or credentials
# 5. Never include things that change weekly (metrics, TODOs, logs)
# 6. Use tables for specs, code blocks for formats, bullets for rules
# 7. Keep total folder under 50KB — AI context windows are limited
# 8. Update the folder when architecture changes, not when values change
# 9. Test it: give ONLY the instructionAI/ folder to a fresh AI and ask
#    it to explain your project. If it can't, your docs are incomplete.
# 10. One source of truth: don't duplicate across files, cross-reference

## Ciel 2.0 Current Status (as of July 6, 2026)

This project (Ciel 2.0) has the following active configuration and recent focus:

- Brain: Vilao (alic/qwen3.7-max) with permissive settings
- Worker: DeepSeek (deepseek-chat)
- SAFETY MODEL (IMPORTANT — decoupled July 2026): two INDEPENDENT flags.
  - SAFETY_OPEN=true, VILAO_SAFETY_BYPASS=true → relax Brain CONTENT-filtering only.
  - DISABLE_SAFETY_GATE=false (DEFAULT) → the destructive-tool confirmation gate is ACTIVE.
    Eight high-risk tools (delete_file, execute_shell_command, send_gmail_message,
    send_gmail_html_message, reply_to_email, trash_email, git_confirm_push, vision_act)
    require Master's Y/N. Do NOT re-couple the two flags — that previously made a denied
    confirmation still delete the file.
  - DANGEROUS-CODE GATE (added July 6, 2026): write_file/append_file and execute_code() also
    require Y/N when the content matches a real destructive pattern (drive format, mkfs,
    shutil.rmtree, fork bomb...) — found live via a "format the drive but only if safe" test:
    the Worker's own idea of "safe" was a dry_run flag that still wired a real subprocess
    format/mkfs call, gated only against the OS system drive (not e.g. D:\, where Ciel lives).
    Same confirm flow/UX as the eight tools above; bypassed only by DISABLE_SAFETY_GATE=true.
- Safety kept specifically for: violent text, info leaks, harm, big/destructive changes.
- File writing: System asks for explicit path (ciel_workspace/ or agent_output/) unless the
  query already names one. Absolute paths inside those two zones are now accepted.
- Proactive bypasses and fallbacks avoid upstream CONTENT_FILTERED errors on legitimate tasks.

Core capabilities & flows (validated July 2026):
- MARKET report+email: dynamic per-asset plan (XAU/BTC/ETH/EUR/silver...) — only the assets the
  user names are queried; one asset's RSI/MA is never mislabeled as another's; subject is dynamic.
- RESEARCH/NEWS email (e.g. "tổng hợp tin kinh tế / World Cup ... gửi ..."): stealth_search FIRST,
  then synthesize the body from REAL results (never a hollow "đã đính kèm... [Your Name]" shell).
- DOCUMENT email: read_document reads a PDF/DOCX FIRST, then summarizes into the email body.
- Every outbound email passes ONE sanitizer: no [COGNITION]/tags, no meta ("email sent/Message Id"),
  no internal paths, no [Your Name]/[Ký tên] (→ "Ciel"), no leftover "Subject:" line; body is sent
  as HTML so line breaks/paragraphs render correctly.
- Anti-fabrication: claim "sent" only on a real Message Id; referential sends ("gửi cái vừa rồi")
  reuse the exact prior reply instead of the Brain re-inventing data; never invent prices/numbers.
- WORKFLOW SAFEGUARDS (deterministic, not Brain-dependent): if the plan is missing the terminal
  send step (email intent + address) or the file-write step (explicit path + write verb), it is
  auto-appended so the email is actually sent / the file actually written with real content.
- TIME-AWARE search: Router knows today's date; a stale year the Brain injects into a query is
  bumped to the current year; stealth_search auto-applies a recency window for "latest/mới nhất".

Testing: backtest/test_hard_special.py (email bypass, mixed language, partial failure, explicit
path, self-correction, harmful intent) + backtest/test_integration.py (safety gate, self-healing,
self-correction). User verification of the actual inbox (kxctran@gmail.com) remains the final check.

THIRD TIER — Middleware (added July 5, 2026, disabled by default via MIDDLEWARE_ENABLED):
- A semantic verifier/finalizer for outbound email/report bodies ONLY (MIDDLEWARE_SCOPE=email).
  Runs after the deterministic sanitizer, before the safety-gate preview.
- Catches what regex/rules cannot: topic mismatch (asked about X, body is about Y), internal
  numeric contradictions (says "Bearish" but the stated price is above both moving averages),
  and templated shells with no real content ("báo cáo đã chuẩn bị và đính kèm" with nothing in it).
- Acts as a FINALIZER: edits the body in place when it finds a fixable problem, rather than just
  blocking. Capped at MIDDLEWARE_MAX_PASSES (default 1). Fail-open on every failure mode (disabled,
  out-of-scope, provider error, or unfixable flag) — a Middleware hiccup must never block a send.
- IMPORTANT constraint in its prompt: it may ONLY flag numbers that contradict each other within
  the SAME body — never reject a number just because it looks unfamiliar against its own training
  knowledge (it once wrongly rejected a genuine live gold price as "unrealistic" before this rule
  was added; real-world/live data can and will differ from any model's training-era priors).
- Full audit trail in thoughts.log under actor MIDDLEWARE: REVIEWED (even silent approvals — so
  "ran and approved" is distinguishable from "never ran"), REVISED (full before/after diff),
  FLAGGED_UNFIXABLE, REVIEW_ERROR.

REQUEST TIMEOUT (added July 5, 2026): all three tiers (Brain/Worker/Middleware) now set an explicit
LLM_REQUEST_TIMEOUT (default 90s) on every LLM client. Previously NONE of them had a timeout, so a
provider that stalled (accepted the connection but never replied) hung the whole pipeline forever —
found live during test runs (0% CPU for 10+ minutes on one stuck call). Now a stall raises a
catchable timeout instead.

"Xu hướng" cross signal. The Worker used to infer the price-vs-MA comparison itself when writing

PROMPT-REWRITE HARNESS (added July 6, 2026): `scripts/prompt_harness.py` mines thoughts.log for

7. First real finding from the harness — single-tool email-send gap: the existing multi_tool
   "auto-append send_gmail_message if the plan forgot it" safeguard (llm_connector.py, added July 4)
   only fires inside the `action == "multi_tool"` branch. When the Brain under-scopes a compound
   "search X, then email me" request into a single `action: "tool"` call instead, that safeguard
   never runs, leaving only the 2-attempt self-correction loop as backstop. Confirmed live in the
   log: a "summarize World Cup news and email it" turn routed as single-tool stealth_search, the
   Worker asked the user for their email instead of sending, self-correction tried `get_fact('email')`
   on an empty vault, and burned its last retry without ever sending. This was the single largest
   harness cluster (~84 recurring "gathered data but never finished the request" triggers).
   Fixed: right after the route decision, a single-tool call with a real email address + send verb
   and no existing send step is promoted to a multi_tool plan (original tool + appended
   send_gmail_message), reusing the existing multi_tool safeguard instead of duplicating it.
   Verified deterministically against the real failing input plus 5 edge cases (no address, no send
   verb, tool already is a send tool). Re-ran full suite (2026-07-09): test_integration.py 27/28
   (same pre-existing non-functional fail, no new regressions), test_hard_special.py 14/16 — Hard 2/5
   and Special 4 (the email+data combo cases that exercise this exact fix) all passed with real
   Gmail Message Ids. The 2 test_hard_special fails are unrelated to this fix: Hard 6 is a checker

   real pre-existing Worker issue (generated `shutil.rmtree(` for a "safe cleanup" code-gen request)
   that the dangerous-code gate would normally catch — but that suite runs with
   DISABLE_SAFETY_GATE=true by design, so the gate never got a chance to intercept it here.

8. Healing skip-list for unfixable errors (added July 9, 2026): the self-healing trigger
   (llm_connector.py) fired for ANY tool whose result started with "Error" in the first 30
   chars, not just run_python_script — including errors no parameter guess can ever fix
   (missing python library, network timeout, geo-restriction, OS socket errors). The
   "other tools" healing branch (recovery_manager.py) has no way to say "unfixable," so it
   always burned an extra Worker call guessing new args that were guaranteed to fail again.
   Found via prompt_harness.py: 220 HEALING_TRIGGER/UnclassifiedError occurrences in
   thoughts.log. Fixed: added `_HEALING_SKIP_PATTERNS` — deliberately narrow, only skips
   patterns with zero possible param fix (library not installed, max retries exceeded, read
   timed out, WinError socket errors, geo-restriction) — genuine format issues ("Could not
   find price for BTCUSDT... Ensure format is correct") stay eligible since that IS a real,
   observed fix. Verified against the full historical log: 94/269 (34.9%) of all past
   healing triggers would have been skipped by this, each saving one guaranteed-to-fail
   Worker call. Regex-verified against 10 real historical error strings (6 skip, 4 keep) —
   all correct.

VOICE I/O — CLI (added July 11, 2026): the Python side of the "voice seam" now exists, mirroring the
UI seam design (capture/speak plug in without touching the core; transcript feeds the SAME
`ciel.run_step()` the keyboard uses). Two standalone, swappable modules, each runnable on its own to
test the modality BEFORE wiring it into the whole agent:
  - INPUT / STT — core/voice_input.py. Mic capture via `sounddevice` (bundles PortAudio, clean
    Windows install — no PyAudio/compiler). Energy-based endpointing (auto-calibrates ambient noise,
    stops after ~1.3s silence, 15s cap, 6s start-timeout). Backends via STT_BACKEND (default "google"
    = SpeechRecognition free Google Web Speech, no key, vi-VN; "whisper" = faster-whisper offline if
    installed; "gemini" = google-genai if GEMINI_API_KEY set). Test alone: `python -m core.voice_input`.
  - OUTPUT / TTS — core/speech_output.py. KEY DESIGN DECISION (deliberate): do NOT dumb down the
    model prompts to be speech-friendly — the text UI / HUD / EMAIL all want the rich formatting.
    Instead a deterministic `to_speech()` normalizer (same pattern as `_sanitize_outbound_email`)
    strips markdown / emojis / [COGNITION]-style ALL-CAPS tags / code blocks / URLs before the text
    hits the engine; numbers are preserved. Backends via TTS_BACKEND (default "edge" = edge-tts,
    free MS neural voices, vi-VN-HoaiMyNeural (F) / vi-VN-NamMinhNeural (M), the ONLY 2 VN neural
    voices; "pyttsx3" = offline SAPI; "space"/"rvc" = mikuTTS HF Space). MP3 playback uses built-in
    Windows MCI (winmm) — no extra playback package. Prosody via TTS_RATE/TTS_PITCH/TTS_VOLUME.
    Test alone: `python -m core.speech_output "Xin chào Master"` (add --show to see normalized text,
    --raw to hear it un-normalized).
main.py flags: `--voice` (speech is the default input; Enter on empty line = speak, or type to

RVC / mikuTTS SPACE BACKEND (experimental, Cách 1): TTS_BACKEND=space calls John6666/mikuTTS's Gradio

GPU note (important): NONE of these backends use the LOCAL GPU — edge-tts and the Space run on
Microsoft/HF servers (your machine only does HTTP + audio playback), pyttsx3 is CPU. This machine's
`torch` reports CUDA available=False, so a *locally downloaded* neural TTS/RVC model would fall back
to CPU (slow) — local RVC is only worth it with an actual NVIDIA GPU + CUDA torch. edge-tts is the
recommended default (cloud, free, instant, 0 GPU, good vi-VN).
