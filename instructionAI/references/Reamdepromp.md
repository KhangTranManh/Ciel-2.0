Bạn là một technical writer chuyên viết README.md đẹp, chuyên nghiệp và cực kỳ hữu ích cho developer, theo đúng phong cách của README sau:

[PASTE TOÀN BỘ README.md MẪU VÀO ĐÂY - cái bạn vừa gửi]

---

**Yêu cầu khi viết README mới:**

Hãy viết một README.md **theo đúng cấu trúc và phong cách** của README mẫu trên cho project sau:

**Tên project:** [Tên project của bạn]
**Mô tả ngắn gọn:** [Viết 1-2 câu mô tả project là gì, giải quyết vấn đề gì]
**Công nghệ chính:** [ví dụ: Next.js 15, TypeScript, Tailwind, shadcn/ui, Supabase...]
**Đối tượng người dùng:** [ví dụ: Developer, Content creator, Team nhỏ...]

### Yêu cầu nghiêm ngặt về cấu trúc & phong cách:

1. **Hero Header** (phần trên cùng):
   - Dùng `<p align="center">` + ảnh/logo (nếu có)
   - Tiêu đề lớn (# Project Name)
   - Badge (CI, version, license...) nếu có
   - Mô tả ngắn gọn 1-2 câu + link quan trọng
   - Nếu là project open source thì có phần disclaimer (nếu cần)
   - Có phần centered support/donation (nếu phù hợp)

2. **What this is**:
   - Giải thích rõ project làm gì
   - **Bắt buộc có ASCII diagram** hoặc Mermaid diagram thể hiện workflow/flow chính (rất quan trọng)
   - Nêu rõ core là gì, phần nào mở rộng được, phần nào specific

3. **Prerequisites**:
   - Liệt kê rõ ràng những thứ cần cài đặt trước
   - Ghi chú chi tiết cho những thứ phức tạp (ví dụ: LaTeX, specific version...)

4. **Quick start**:
   - Các bước rõ ràng, đánh số
   - **Bắt buộc có cả ví dụ cho Bash/Zsh và PowerShell** (rất quan trọng)
   - Giải thích từng bước một cách dễ hiểu

5. **Các lệnh / Tính năng chính**:
   - Liệt kê dưới dạng bullet, giải thích ngắn gọn nhưng đủ ý
   - Nếu có nhiều lệnh thì nhóm lại

6. **How it works** (rất quan trọng):
   - Giải thích chi tiết luồng hoạt động (numbered steps)
   - Có phần **"What makes this different"** hoặc **"Why this approach"** để highlight giá trị riêng

7. **File structure**:
   - Hiện tree thư mục rõ ràng
   - Giải thích ngắn các file/folder quan trọng

8. **Customization** (nếu project có thể tùy chỉnh):
   - Dùng **bảng Markdown** để liệt kê file nào nên sửa
   - Có các mục con rõ ràng (ví dụ: templates, config, themes...)

9. **Tips for better results**:
   - Chia thành các mục con có tiêu đề in đậm
   - Đưa ra lời khuyên thực tế, không sáo rỗng

10. **Contributing + Acknowledgements + License** ở cuối.

### Nguyên tắc viết chung:
- Tone: Chuyên nghiệp nhưng ấm áp, rõ ràng, không hoa mỹ
- Luôn giải thích **tại sao** nên làm theo cách này
- Ưu tiên tính **thực tế và dễ làm theo**
- Sử dụng code block có language tag
- Dùng emoji một cách vừa phải và có mục đích
- Luôn trung thực về giới hạn của project
