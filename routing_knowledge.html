Ciel 2.0

Complete Problems & Knowledge Gaps

Everything we have encountered across routing, models, synthesis, execution, testing, and architecture

System Overview

Ciel 2.0 is a modular Brain-Worker agent. The Brain (currently Vilao/Qwen-based) is responsible for routing and planning. The Worker (DeepSeek) is responsible for synthesis and content generation. Tools are executed via ToolManager, with multi-tool flows, self-correction, RAG memory, and proactive scheduling.

Many changes have been made to support complex real-world tasks (especially market data + professional email reports), but underlying problems keep surfacing in different areas.

All Major Problem Areas We Have Encountered

High

1. Routing Knowledge & Brain Reliability

Core Issues:
• Brain (Vilao/Qwen) frequently triggers CONTENT_FILTERED on normal intents like "send email", "send report", "gửi báo cáo".
• Heavy early bypass logic was required in llm_connector.py because the Brain cannot be trusted for email + multi-tool flows.
• Router prompt is outdated — still references old Report.pdf and forces specific send_gmail_message + fixed templates.
• When user tried switching to custom "gx/gpt-5.5" via BRAIN_PROVIDER=GPT, no branch existed → fell back to Gemini (no key) or kept using Vilao path with wrong model string.
The Brain is not doing its primary job (intelligent routing + planning) for the exact complex tasks the user cares about. Most real email flows bypass the Brain entirely.
High

2. Model Selection & Provider Switching

• Current combo (Vilao/Qwen Brain + DeepSeek Worker) requires constant workarounds (bypass, extra cleaning rules, prompt softening).
• Switching models is brittle: no generic "openai" / "gpt" / custom-gateway provider branch in brain.py. Only ollama, deepseek, vilao, else=Gemini.
• Attempts to use "gx/gpt-5.5" resulted in 403 "subscribe to model" errors during every Brain.plan() call in integration tests.
• Model name strings containing # or prefixes get passed literally and fail on the backend.
• No clean way to point Brain to a different OpenAI-compatible endpoint without forking the provider logic.
The architecture makes it painful to upgrade the Brain (the most critical component for multi-agent tasks). Tests break immediately on model changes.
High

3. Worker Synthesis Quality & Email Content

• Worker frequently produces chatty output ("Master,", internal thoughts, meta tags) that leaks into emails.
• Professional email bodies require heavy post-processing and strict rules in format_task + persona.
• Early versions sent placeholders, hallucinated prices, or wrong structures because synthesis happened before data.
• The "Professional Email by Default" direction was created precisely because previous synthesis was not reliable enough for real inbox use.
The system can gather data, but turning that data into something a user would actually want to receive in email is still fragile.
High

4. Data Flow, Parsing & Structured Results

• Most tools return loose strings. Report builders (and email synthesis) rely on regex parsing or fragile string matching.
• _build_market_html_from_results and similar helpers contain cleaning logic that strips "Master", meta, etc.
• No consistent structured data objects flowing between tools, Brain, and Worker.
• Partial tool failures (e.g. XAU price "no data") are handled inconsistently.
Small changes in tool output format break downstream report/email generation. This has been a recurring source of bugs.
Medium

5. Multi-Tool Execution & Send Separation

• Special "run non-send tools first, then re-execute send with synthesized body" logic lives in execute_multi_tool and keeps growing.
• Separate handling for send_gmail_message vs send_gmail_html_message + special dashboard builder.
• Self-correction exists but is not reliably applied to the final email synthesis step.
• Adding new report types (todo, health, alerts) forces more special cases.
The execution layer has become a collection of workarounds rather than a clean data-first → synthesize → deliver pattern.
High

6. Scattered & Inconsistent Knowledge

• Routing rules live in router prompt, persona/official_ciel_personality.txt, gmail_ops prompt, llm_connector format_task, and note.txt.
• After adding HTML dashboard then switching to "Professional Email by Default", many places still reference the old fixed template.
• note.txt was updated, but router prompt and brain.py still contained old Report.pdf language for a long time.
• Every new feature (email bypass, dashboard, model switch) requires manual synchronization across many files.
The agent receives conflicting instructions. Changes in one place are frequently forgotten in others.
High

7. Testing Gaps & Model Sensitivity

• Integration tests and hard_special tests frequently crash at CielCore init or first Brain call when models change.
• Many tests were written assuming the old Vilao + fixed template world.
• Recent gx/gpt-5.5 experiments caused almost every test to fail at the "Please subscribe to model" stage.
• Real inbox verification is still the only reliable way to know if a professional email actually looks good.
• No good coverage for partial tool failures + email synthesis, or for new provider branches.
The test suite is a source of friction rather than confidence when trying to evolve the system (especially models or email flows).
Medium

8. Generalization & Adding New Capabilities

• Market dashboard was very specific. Adding health_report.html showed there is no reusable "report type" system.
• Every new email/report type risks duplicating synthesis rules, builder functions, and prompt guidance.
• Path asking, safety gates, and write destinations have similar "we had to special-case this" history.
• The "Professional Email by Default" idea is a step toward generalization, but the underlying machinery is still fragmented.
The system is harder to extend than it should be for a multi-agent design.
Medium

9. Other Recurring Issues

  • Path leaks: Repeated rules needed across prompts to prevent agent_output/ and ciel_workspace/ from appearing in emails.
  • Safety gate interaction: Email sending is high-risk but often bypassed for convenience; consistency is hard.
  • Write destination: System now asks for path unless specified, but this behavior is scattered across system_ops, router, and Brain prompts.
  • Language handling: Vietnamese + English mixed requests require careful persona + synthesis rules.
  • Early vs late synthesis: The "data first then send" pattern had to be enforced multiple times in different places.

Mental Model of the Current System

Brain = the strategist, but often blocked or bypassed (especially on email).
Worker = the writer, but tends to be chatty unless heavily constrained.
Bypass = emergency direct orders that now carry most of the real logic.
Tools + multi-tool = data collectors (mostly strings).
Synthesis = the step that still needs the most babysitting to produce professional output.

The system can do powerful things, but many of the "powerful things" the user actually asks for (check market + send real professional email) required building parallel paths and extra guardrails because the core routing + synthesis loop was not strong enough on its own.
